CentralPoint: inkonsistente Daten

Letzte Änderung 30.08.2026 · Version 3 · Seiten-ID 729

Entwurf – diese Seite ist noch nicht geprüft und kann Fehler enthalten.

Wenn Bediener doppelt erscheinen, Artikel sich je Filiale unterschiedlich verhalten oder Belegpositionen ohne gültige Mehrwertsteuer geführt werden.

Symptome

  • Falsche oder fehlende Mehrwertsteuer auf Belegen und Positionen.
  • Bediener doppelt geführt oder falsch zugeordnet.
  • Artikel mehrfach vorhanden oder je Filiale unterschiedlich im Verhalten.
  • Fehler beim Start des CentralPoint oder beim Aufruf der eigenen Berichte, ohne dass eine Fehlermeldung angezeigt wird.
  • Bediener erscheinen als angemeldet, obwohl es sie nicht mehr gibt.

Ursache

Meist Duplikate zwischen filialspezifischen Datensätzen und Zentraldatensätzen: Ein Datensatz existiert einmal für eine bestimmte Filiale und einmal zentral. Korrekt ist immer der Zentraldatensatz — also der mit der Filialkennung 0.

Die zweite Gruppe sind verwaiste Verweise: Eine Belegposition zeigt auf eine Steuer, die es nicht mehr gibt, oder eine Sitzung auf einen Bediener, der gelöscht wurde.

Vorgehen

  1. Sechs Prüfungen auf der CentralPoint-Datenbank ausführen — ausschließlich lesend:
Prüfung Findet Betroffener Bereich
Doppelte Artikel Artikel, die sowohl filialspezifisch als auch zentral vorliegen Artikel
Doppelte Bediener Bediener, die sowohl filialspezifisch als auch zentral vorliegen Bediener
Verwaiste Steuerzuordnung Belegpositionen, deren Steuerkennung in ipos_tax nicht existiert Mehrwertsteuer, Umsätze
Artikel ohne Mehrwertsteuer Artikel, bei denen weder am Artikel noch an Warengruppe noch an Hauptgruppe eine Steuer hinterlegt ist Mehrwertsteuer, Stammdaten
Artikel nur in der Filiale Artikel mit Filialdatensatz, aber ohne Zentraldatensatz Artikel, Replikation
Verwaiste Sitzungen offene Anmeldungen auf Bediener, die in ipos_operators nicht existieren Bediener, Anmeldung

Beteiligte Tabellen: ipos_registerarticles, ipos_operators, ipos_receiptpositions, ipos_tax, ipos_groups, ipos_maingroups, ipos_loggedinoperators.

Die Abfragen sind so gebaut, dass sie nur bei einem Fund eine Zeile liefern. Bleibt eine Abfrage ohne Ergebnis, liegt die jeweilige Inkonsistenz nicht vor. Die Prüfungen 1 und 2 geben zu jedem fehlerhaften Datensatz zusätzlich die Kennung des korrekten Zentraldatensatzes aus (CorrectArticleId, CorrectOperatorId) — beide Kennungen gehören ins Ticket.

-- Prüfung 1: Doppelte Artikel (Filiale und Zentrale)
SELECT COUNT(*) AS 'CountWrongArticles' FROM (
  SELECT ra.Article_No,
         MIN(ra.ID) AS 'WrongArticleId',
         (SELECT ID FROM ipos_registerarticles
           WHERE Article_No = ra.Article_No AND BRANCH_ID = 0 LIMIT 1) AS 'CorrectArticleId'
  FROM ipos_registerarticles ra
  WHERE ra.BRANCH_ID != 0
    AND ra.Article_No IN (
      SELECT a1.Article_No FROM
        (SELECT ID, Article_No FROM ipos_registerarticles GROUP BY Article_No, ID) a1
      GROUP BY a1.Article_No HAVING COUNT(*) > 1
    )
  GROUP BY ra.Article_No
) t1 HAVING COUNT(*) > 0;

-- Prüfung 2: Doppelte Bediener
SELECT COUNT(*) AS 'CountWrongOperators' FROM (
  SELECT * FROM (
    SELECT o.OPERATORID, o.ID AS 'WrongOperatorId', o0.ID AS 'CorrectOperatorId'
    FROM ipos_operators o,
         (SELECT ID, OperatorId FROM ipos_operators WHERE BRANCH_ID = 0) o0
    WHERE o.OPERATORID = o0.OPERATORID
    ORDER BY o.OPERATORID
  ) x
  WHERE x.WrongOperatorId != x.CorrectOperatorId
  GROUP BY x.OperatorId, x.WrongOperatorId
  ORDER BY x.WrongOperatorId
) t1 HAVING COUNT(*) > 0;

-- Prüfung 3: Verwaiste Steuerzuordnung auf Belegpositionen
SELECT * FROM (SELECT DISTINCT TAX_ID FROM ipos_receiptpositions r) t1
WHERE TAX_ID NOT IN (SELECT ID FROM ipos_tax);

-- Prüfung 4: Artikel ohne Mehrwertsteuer
SELECT COUNT(*) FROM ipos_registerarticles a, ipos_groups g, ipos_maingroups m
WHERE a.GROUP_ID = g.ID AND g.MAIN_GROUP_ID = m.ID
  AND a.BRANCH_ID = 0 AND g.BRANCH_ID = 0 AND m.BRANCH_ID = 0
  AND IFNULL(a.TAX_ID, 0) + IFNULL(g.TAX_ID, 0) + IFNULL(m.TAX_ID, 0) <= 0
HAVING COUNT(*) > 0;

-- Prüfung 5: Artikel nur in der Filiale, nicht in der Zentrale
SELECT * FROM ipos_registerarticles WHERE ID IN (
  SELECT DISTINCT ID FROM ipos_registerarticles ra WHERE ID NOT IN (
    SELECT DISTINCT ID FROM ipos_registerarticles WHERE BRANCH_ID = 0
  ) AND BRANCH_ID != 0
) GROUP BY ID;

-- Prüfung 6: Verwaiste Sitzungen auf nicht vorhandene Bediener
SELECT * FROM ipos_loggedinoperators
WHERE OPERATOR_ID NOT IN (SELECT DISTINCT ID FROM ipos_operators)
  AND Deleted IS FALSE;

Liefert Prüfung 3 Treffer, zeigt diese Abfrage die betroffenen Positionen im Einzelnen:

SELECT * FROM ipos_receiptpositions WHERE TAX_ID NOT IN (SELECT ID FROM ipos_tax);

Prüfung 6 gibt jede verwaiste Sitzung einzeln aus. Notieren Sie zu jeder Zeile die Kassennummer und die Bedienerkennung — an welcher Kasse die Sitzungen hängen, ist der wichtigste Hinweis auf die Herkunft der Daten.

  1. Liefern alle Prüfungen kein Ergebnis, liegt keine der bekannten Inkonsistenzen vor — die Ursache ist dann woanders zu suchen.
  2. Bei Treffern: Anzahl und Kennungen der betroffenen Datensätze dokumentieren und ins Ticket aufnehmen.
  3. Eskalieren.

Keine eigenständigen Korrekturen an der Datenbank. Das Zusammenführen doppelter Datensätze und das Nachpflegen fehlender Steuerzuordnungen erfolgt über die Entwicklung — ein falsch zusammengeführter Bediener oder Artikel zieht Umsatzdaten mit sich.

Zu beachten

Eine bekannte Ursache ist das Zuweisen einer Testkasse mit bereits vorhandenen Daten an einen produktiven CentralPoint — die Daten werden dabei hochrepliziert und erzeugen Dubletten. Testkassen gehören an eine eigene Umgebung.

In einem dokumentierten Supportfall fanden sich über Prüfung 6 zwei offene Sitzungen an einer einzelnen Kasse (<Kassennummer>) auf Bediener, die in den Stammdaten gar nicht existierten. Als Auslöser wurde eine solche hochreplizierte Testkasse vermutet; bestätigt ist das nicht. Häufen sich Treffer auf einer einzelnen Kassennummer, ist die Herkunft dieser Kasse der erste Verdacht.
