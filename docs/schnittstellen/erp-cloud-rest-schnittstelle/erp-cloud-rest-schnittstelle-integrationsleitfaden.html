ERP-Cloud REST-Schnittstelle: Integrationsleitfaden

Letzte Änderung 29.08.2026 · Version 1 · Seiten-ID 766

Entwurf – diese Seite ist noch nicht geprüft und kann Fehler enthalten.

Die ERP-Cloud stellt eine generische REST-Schnittstelle bereit, über die ein externes Kassen- oder App-System Stammdaten abholt und Verkaufs-, Guthaben- und Bonuspunktdaten zurückmeldet. Der Datenaustausch läuft über Benachrichtigungen: die ERP-Cloud legt eine Nachricht an, das externe System holt sie ab und quittiert den Erhalt.

Funktionsweise

Die Schnittstelle arbeitet nach dem Prinzip einer Warteschlange. Jede Änderung in der ERP-Cloud erzeugt eine Benachrichtigung (receivableNotification). Das anzubindende System fragt die offene Liste ab, holt die einzelnen Nachrichten ab und quittiert sie. Erst mit der Quittierung verschwindet ein Eintrag aus der Liste — eine abgeholte, aber nicht quittierte Nachricht wird erneut geliefert.

Der Ablauf in vier Schritten:

  1. Offene Benachrichtigungen abfragen — GET https://<ERP-CLOUD-HOST>/basic/pos/getMessages liefert alle ungelesenen Benachrichtigungen als receivableNotificationList mit den Feldern ID, Type, Recipient und Time. Auf einen einzelnen Typ eingeschränkt: GET https://<ERP-CLOUD-HOST>/basic/pos/getMessages/<Nachrichtentyp>.
  2. Daten abholen — GET https://<ERP-CLOUD-HOST>/basic/pos/getMessage/<ID> liefert den Inhalt der Nachricht mit dieser ID.
  3. Erhalt quittieren — DELETE https://<ERP-CLOUD-HOST>/basic/pos/commitMessage/<ID>. Quittiert wird der Erhalt, nicht die Verarbeitung. Das abholende System ist dafür verantwortlich; die ERP-Cloud quittiert nicht selbst.
  4. Daten zurückmelden — alle schreibenden Vorgänge gehen an denselben Endpunkt POST https://<ERP-CLOUD-HOST>/basic/pos/process.

Für die Erstbefüllung erzeugt GET https://<ERP-CLOUD-HOST>/basic/pos/createInitialNotifications aus den bestehenden Stammdaten alle Benachrichtigungen für einen vollständigen Erstimport.

Daten werden als XML in UTF-8 ausgetauscht. Ein XSD-Schema ist verfügbar.

Den Wert für <ERP-CLOUD-HOST> erhalten Sie je Umgebung von YUVENDA Enterprise Solutions GmbH.

Beteiligte Komponenten

Komponente Rolle
ERP-Cloud stellt Stammdaten bereit, erzeugt Benachrichtigungen und nimmt zurückgemeldete Daten entgegen
Anzubindendes System (Partner-POS oder App) fragt Benachrichtigungen ab, holt sie ab, quittiert sie und meldet Kunden, Guthaben und Käufe zurück
Kasseninstallation des Endkunden liefert die Daten in die ERP-Cloud und übernimmt von dort — nicht Teil dieser Schnittstelle

Nachrichtentypen

Typ Richtung Inhalt
MasterDataNotification Abholen Filialstammdaten: UUID, Name, City, Postcode, Street, Housenumber, Number
ArticleNotification Abholen Artikelstammdaten inklusive Warengruppe, Hauptgruppe, Preis, Steuer, EAN-Liste und Bild (Base64). Ein Filialbezug besteht bei Artikeln nicht
BonusPointTypeNotification Abholen Bonuspunktarten mit Gutschriften (Credits) und Einlösungen (Debits) je Artikel
ConsumerNotification Abholen und Senden Kundendaten; beim Senden ohne Prepaid- und Bonuspunktangaben
ConsumerCreditNotification Abholen Kundendaten inklusive Bonuspunkt- und Prepaid-Guthaben
ReceiptNotification Abholen abgeschlossene Bons inklusive Prepaid- und Bonuspunkttransaktionen
PrepaidTransactionNotification Senden Guthabenbuchungen
OrderNotification Senden Käufe aus dem externen System

Authentifizierung

Jeder Request trägt zwei HTTP-Header:

  • X-Auth-Token — die feste Zugangs-UUID, die den Kunden identifiziert. Sie wird im Klartext übermittelt.
  • X-CSRF-Token — SHA256(<Secret>:TT.MM.JJJJ) als Hex-Zeichenkette. Das Datum ist der Tag des Requests, der Hash wechselt also täglich.

UUID und Secret erhalten Sie von YUVENDA Enterprise Solutions GmbH; Test- und Produktionsumgebung haben eigene Zugangsdaten.

[OFFEN: Im älteren Integrationsleitfaden ist das Beispiel für die Hash-Bildung mit der Zugangs-UUID statt mit dem Secret gebildet. Eine verbindliche Festlegung, welcher Wert vor dem Doppelpunkt steht, fehlt.]

Daten zurückmelden

Alle drei Vorgänge gehen an POST https://<ERP-CLOUD-HOST>/basic/pos/process:

  • Kunden anlegen oder ändern — gültige consumerNotification ohne Prepaid- und Bonuspunktangaben senden. Eine neue UUID legt einen Kunden an, eine bestehende UUID ändert den vorhandenen Datensatz.
  • Guthaben buchen — gültige prepaidTransactionNotification mit Type PREPAID_TOP_UP (Aufladung), PREPAID_PAYMENT (Zahlung mit Guthaben) oder PREPAID_REFUND (Erstattung einer Zahlung mit Guthaben).
  • Käufe senden — gültige orderNotification. Der Type EXTERNAL ist zwingend zu übergeben. Gross und VAT werden je Position übergeben und bilden die Grundlage für die Berechnung von Bonuspunkten; sie dürfen vom Artikelstamm abweichen. Optional sind ein Abholdatum (PickupDatetime) sowie 1 bis n Prepaid- oder Bonuspunkttransaktionen.

Antwortcodes

Code Bedeutung
200 Anfrage erfolgreich entgegengenommen
400 Anfrage ungültig und abgewiesen, eine Wiederholung ist nicht erwünscht
401 Client konnte nicht authentifiziert werden
403 Anfrage gültig, wird aber verweigert, zum Beispiel aus Berechtigungsgründen
404 Ziel nicht verfügbar, gegebenenfalls liegt eine falsche Konfiguration im Client vor
405 Nachrichtentyp wird von der Zielanwendung nicht unterstützt
500 technisches Problem, die Übermittlung sollte wiederholt werden

<receivableNotificationList queryLocation="82f0a808-e38e-47cc-89fa-2b072948b348"
                            furtherNotificationsAvailable="false">
    <receivableNotification>
        <id>4566785</id>
        <type>ArticleNotification</type>
        <recipient>82f0a808-e38e-47cc-89fa-2b072948b348</recipient>
        <time>2024-09-05T12:37:40Z</time>
    </receivableNotification>
</receivableNotificationList>

Zu beachten

Quittieren Sie jede abgeholte Nachricht einzeln per commitMessage, auch wenn die fachliche Verarbeitung im Zielsystem später erfolgt oder fehlschlägt. Ohne Quittierung bleibt die Nachricht in der Liste, die Zahl offener Benachrichtigungen wächst unbegrenzt und der Abruf wird zunehmend langsamer.

  • Die Schnittstelle setzt eine ERP-Cloud-Anbindung des Kunden voraus. An einer Standalone-Kasse ohne ERP-Cloud steht sie nicht zur Verfügung.
  • Artikel werden ohne Filialbezug geliefert. Eine filialabhängige Preis- oder Sortimentssteuerung muss im anzubindenden System abgebildet werden.
  • Die Zugangs-UUID identifiziert den Kunden. Behandeln Sie sie wie ein Kennwort: verschlüsselt speichern, nicht in Protokolldateien schreiben, nicht im Client-Code hinterlegen.
  • Wiederholte Sendungen sind nicht automatisch idempotent. Vergeben Sie je Buchung eine eigene UUID, damit ein Wiederholungsversuch nach einem Zeitüberlauf nicht doppelt bucht.
